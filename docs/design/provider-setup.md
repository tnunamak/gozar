# Provider setup

A host can guide an owner through setup and remove what Gozar created using only public Gozar data. The trusted adapter supplies the provider knowledge. Gozar binds each offer to its authority and retains enough evidence to recover from interrupted writes.

## Render the current action

Find setup actions in `Candidate.setup.actions`, provider prerequisite remedies, or the current draft configuration. An action with a `step` descriptor opts into the setup operation API. Legacy direct configuration actions continue to use their scoped setup approval without an operation. An adapter derives its current offer from observed state and the operation's confirmed outcomes. Trusted adapter observation and execution stay distinct. Gozar projects status and ownership from readback and the private journal. Gozar verifies prerequisites before admitting an effect. An app displays the next action, collects its input, and sends back the exact IDs, revisions and digest that Gozar supplied. Action IDs and option values are opaque.

| Offer | Host behavior |
| --- | --- |
| `provide-value` with `step.options` | Show the supplied labels. Send the selected opaque value. Gozar checks membership against the current offer. |
| `open-url` with `step.browser` | Request the transient URL with `readSetupOperation({ ...ref, includeBrowserHandoff: true })` and open it in the system browser. Respect the poll interval and expiry. Browser return can prompt an immediate status read subject to the interval. |
| `provide-secret` | Use `storeSecret` for the same input, owner, scope and configuration revision. Send only the resulting handle through `runSetupAction`. |
| `gozar-runs` or `install-artifact` | Render the redacted disclosure and exact consent facts, including capabilities and effects. Return approval only after authorization. |
| `instructions` | Show the actor, permission, instructions and verification source. External work might require a provider administrator, OS permission, or a trusted client. Re-read for evidence. |

`Action.kind` chooses the control. `step.actor`, `permission` and `verification` identify who can do the work, which permission is needed and where completion can be verified. These fields are descriptive. Host capability observations alone confer no authority. A machine driver can execute only with an already granted exact authorization. If human authority is needed, the response is `authorization-required` with the current offer. A known unmet prerequisite is `blocked`. Instructions are rendered as text and never interpreted as commands.

Gozar returns `pending` while the adapter awaits an observation. `denied` and `expired` require evidence tied to the current operation. `complete` is the trusted adapter's setup workflow status. Read `evidence` separately for the observed outcome and its source, or for its unknown status. Uncertain resource debt requires reconciliation. Browser return, process exit and acknowledgement of instructions supply no independent proof. Route publication requires its own route consent and proof. A completed workflow can still offer route guidance or an optional configuration change. Use `state` for setup readiness and render `nextAction` independently. An instruction can also appear while setup is blocked or reconciling.

| Display separately | What it tells the user |
| --- | --- |
| `state` | Progress of the setup workflow. `complete` is not route readiness. |
| `nextAction` | The current offer, if any. Show it even after setup completes. |
| `evidence` | The observed outcome and its source, or that the outcome is unknown. |
| Route publication | Whether the separately approved route passed proof and can be advertised. An allocated `origin` is not enough; use only `published` from the route view. |

**Historical design rationale:** The [cloudflared source study](https://github.com/cloudflare/cloudflared/tree/095f3caf1dd9084cfe063ca40a4e5b0709e53e5b), captured on 2026-11-11, distinguished login or process success from independent certificate and DNS readback. The [Tailscale Serve docs](https://tailscale.com/kb/1312/serve), captured on 2026-11-12, required tailnet HTTPS to be enabled. These examples informed the separation above; they are not current provider-policy claims.

## Open, read and advance

1. Save a caller-chosen `operationId` before the first call. Call `runSetupAction` with that ID, `expectedSetupRevision: 0`, the initial `actionId`, and the configuration or draft revision. Start reserves the operation and returns its first scoped offer. It accepts no approval or input at revision zero and performs no external mutation. The legacy call returns `setup_required` for an operation-only action.
2. Advance with `runSetupAction` using the current setup revision, action ID and configuration revision. Pass the existing setup approval and input where requested. The setup consent scope adds the operation ID and revision. Gozar recomputes the disclosure and current consent facts under that scope before running an effect. Changed facts, stale configuration, an approval copied across operations or scopes, and altered replay input all refuse before effects.
3. Call `readSetupOperation` with home, owner, provider ID and operation ID on restart or while waiting. It reads the persisted operation and may refresh observations. It never allocates, deletes or grants access. An authorization exchange that needs a write runs as a separately admitted machine action. Pending browser handoffs may expire while the host is absent. Denial and expiry carry no grant. A retry is a fresh offer, with a new setup revision and handoff.
4. Call `cancelSetupOperation` with the same reference. Cancel is idempotent and prevents new provisioning or grant advancement. It preserves exact recovery state and allows separately approved reconciliation, removal, revocation and disconnection under the retained scope and current authority. A completion reported after cancellation can update the cleanup evidence and cannot advance provisioning.

The private journal binds the canonical home, owner, registry, provider and applied configuration or draft scope. A setup revision changes when the authority or actionable state changes, including when setup itself commits a new configuration revision. Display-only timestamps do not change it. The current action carries the current consent snapshot. Historical approvals remain tied to their admitted command. A successful replay of the same command returns the latest safe view of its operation, including cancellation or cleanup, and cannot run the command again. A different action, approval or input for the same admitted revision is an operation conflict. Reading and cleaning up a partial operation still use its retained scope when its draft is stale or unavailable.

## Keep provider authority separate

Provider authorization grants provider permissions. Gozar setup approval grants an exact setup effect. The route approval binds the exact application exposure. Every effect needs authority from its controller. One ceremony can cover multiple grants only when one controller can enforce the complete known grant and the review names all effects. Discovery after a login can change the account, resource, cost or target and requires a fresh review before provisioning.

The management grant stays in the host secret backend and is accessible only to the admitted setup and cleanup paths. The connector receives only its exact, scoped connector credential. Public configuration reports credential presence. Status, evidence, errors, events and receipts carry no raw credentials or secret handles. An assisted action can identify the exact provider resource the owner needs to check. A live browser handoff can carry a transient URL for navigation. The trusted interactive host explicitly requests the handoff. Gozar omits the URL from default results and commits only the safe handoff subject and authority facts to consent. Inventory, logs, events, persisted receipts and machine summaries omit that material and all grant codes and bearer data. On recovery Gozar exposes a still-valid handoff or a fresh offer according to the provider's rules.

## Reconcile and remove exact resources

Before each external write, durably journal the admitted action and a private intent that identifies the desired resource and the provider's reconciliation key. Mark the write as in flight before issuing it, then read the result back against the intended subject. A lost response or local persistence failure leaves the intent in `reconciling`. Replaying the admitted command can reconcile that intent. A new create requires reliable evidence that the first effect never took place and can no longer take place, then a fresh offer. An inconclusive lookup keeps debt and offers reconciliation. A provider without sufficient reconciliation guarantees stays blocked for manual verification.

Public `resources` rows carry opaque handles, the last observed presence and removal state. Ownership comes from the journal and exact readback. Matching a name or seeing an existing remote resource supplies no deletion authority. `adopted` and `foreign` rows are retained, including shared prerequisites. `unknown` rows retain unconfirmed removal debt. An owned resource can move to confirmed only after exact absence readback. Credential readback can establish that a token is no longer current. Existing connector inactivity requires separate evidence. The handle identifies the exact journal row across restarts.

Stopping the connector, removing owned provisioning resources such as the tunnel and DNS record, and revoking owned credentials are distinct actions. Removal offers use `step.resourceHandle` and bind the exact resource into consent. An assisted removal describes the work for the owner and leaves debt until Gozar observes exact absence. Gozar rechecks ownership and identity before automated removal and records readback afterward. Where the provider couples effects, the review lists every affected owned resource and requires authority for all consequences. Disconnecting a local reference is separate from revocation. Keep a recovery path for missing management authority as long as debt remains. A discarded draft or cancelled setup never clears debt.

## Adapter observations and execution

An adapter implements `observeSetup(ctx, operation)` and `executeSetup(ctx, command)`. The read receives the operation identity, cancellation state and private resource rows. It returns a state, current action, optional evidence and exact resource observations. Evidence names the operation, verified step and observation time. An action's prerequisites describe dependencies for the host. The adapter decides when the observations justify offering it.

An allocation offer supplies a kind, label and stable subject. Gozar records the subject and a unique intent ID before dispatch. The executor can checkpoint an identity from the admitted provider response via `recordAllocation`. Ownership requires later exact provider readback or an equivalent provider-supported correlation to that intent. Each resource observation repeats the intent ID and subject, supplies its observation time and identifies the exact immutable resource if present. Absence must rule out delayed completion. An unidentified allocation or an inconclusive read keeps debt. A previously allocated subject cannot be rearmed in the same operation.

The observation context exposes configuration values and credential presence through `configurationPresence()`. Operation-held management grants live outside configuration. Use `hasManagementSecret(slot)` to check retention under the current operation without opening the backend or reading bytes. An admitted executor may read the exact input, retain it in a private management slot, or bind a connector credential in the existing configuration. An approved command dispatches once. A new cleanup command gets its own approval. The route lifecycle still supplies transport proof and connector stop. The optional adapter `routeGuidance` callback receives that current route view, its observed listener port when available, and the scope's approved plain values. Gozar checks the existing route operation and exact handle generation, then returns the guidance through `RouteView.binding.remedy`. The callback does not write a setup operation or carry setup approval. An owner-managed route starts with a configured upstream target. A missing observed gate stays unknown.

## Provider capability decisions still open

- Cloudflare managed setup accepts a scoped REST API token through assisted intake. It enumerates active zones and their accounts, creates a remote-managed tunnel, writes its loopback mapping and proxied CNAME, and captures the tunnel run token in the connector secret backend. Browser-only management remains unverified. It would need a third-party client and a grant with the right REST audience, account/zone scope, token retrieval and DNS create/read permission. The cloudflared login certificate does not establish that grant.
- Cloudflare DNS removal is an owner action. The DNS endpoint supplies no documented compare-and-delete precondition, and a same-ID edit can race a preceding API read. Gozar gives the owner the exact record and checks absence after the owner removes it. A lost create response without an immutable receipt remains unresolved. Cloudflare run-token rotation is a dashboard step with API readback of the current token. Existing connectors must also stop. The imported management token can be forgotten locally and revoked separately at Cloudflare.
- Ngrok's management API documents agent authtoken creation. The public MCP metadata lists `credentials:write`, and its docs say tools do not return secrets. Authenticated MCP tool support, token audience and one-time secret delivery remain unverified. Secure intake remains available where the management grant cannot deliver the connector credential. The operation offers an approved disconnect for a retained local inventory key after switching to the dashboard, cancellation or draft staleness. If deletion fails, the operation keeps the offer and requires fresh approval to retry. Local disconnection preserves the agent credential, imported account key and remote domains.
- Tailscale's isolated CLI reported `NeedsLogin` and a browser handoff. Exact node and tailnet identity, admin completion, Serve/Funnel mapping readback and independent client proof remain unverified.

These results select the adapter's offered steps and evidence source. Management and connector credentials remain distinct in all three cases.

Existing raw ngrok TCP/TLS are detect-only. Own-address is adopt-only. These profiles do not get a managed create offer.

## CLI and acceptance

For a project-local install, use `npx --package=@tnunamak/gozar@0.5.5 gozar setup-operation SUBCOMMAND --request-file FILE --json`, replacing `SUBCOMMAND` with one of `reserve`, `read`, `run` or `cancel`. Put the public request or reference in a mode 0600 file. For secret intake, select `run` and add `--secret-file FILE`. An explicit interactive `read --browser-handoff` returns an unexpired handoff when the adapter offers one.

From a [prepared source checkout](../../README.md#develop), not from the installed npm package, run `node --test test/acceptance/provider-setup.red.test.mjs test/acceptance/cloudflare-managed-setup.test.mjs` explicitly. The first suite uses a randomized provider and exercises the same operations through the package root and CLI. The second intercepts the real Cloudflare adapter's REST and connector calls and drives actual loopback gate and app traffic. Cloudflare account permissions, browser enrollment, external reachability and provider-side cleanup still require live acceptance.
